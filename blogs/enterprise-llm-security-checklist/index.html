Access Control

Who can access LLM systems and what data

  • •Authentication required before any LLM interaction, with integration to enterprise SSO (OIDC, SAML) and MFA enforcement for privileged operations. Systems without authentication create open APIs that anyone can query, risking data exposure and operational cost abuse. Security review must verify that all endpoints require valid tokens, session management includes timeouts, and refresh tokens rotate properly to prevent session hijacking where stolen tokens remain valid indefinitely, allowing attackers continued access after credential compromise.
  • •Authorization at document and capability level ensures users only access permitted data and actions. RAG systems must enforce document-level permissions, filtering retrieved chunks by user access rights before context assembly. Without fine-grained authorization, users may retrieve documents they shouldn't access through search, even if not directly displayed, because retrieved chunks processed during generation could leak information through model responses or inference. Security audit requires testing with users having different permission levels, verifying that no query retrieves unauthorized documents, and that responses never reveal information from unauthorized sources even indirectly.
  • •API rate limiting and usage quotas prevent abuse and cost overruns. Production LLM systems need per-user, per-IP, and per-endpoint limits aligned with expected usage patterns. Without limits, compromised credentials or automated scripts could generate millions of queries, incurring substantial API costs or degrading service for legitimate users. Security configuration requires tiered limits (burst, sustained, daily) with appropriate HTTP error responses and monitoring for violation patterns, because unbounded usage risk includes both financial exposure from excessive API calls and denial-of-service where few users consume all available capacity.

    Data Leakage Prevention

    Preventing training data exposure

    • •Prompt logging must exclude sensitive information like PII, credentials, or proprietary business data. Logs containing raw prompts create data breach risk if log storage compromised. Security review requires verifying log sanitization before storage, with sensitive field redaction or exclusion. Logging configuration should distinguish between metrics (counts, latency, error rates) and content (queries, responses), storing content only with explicit user consent and retention policies because detailed logs useful for debugging but create attractive target for attackers, requiring encryption at rest and access controls more stringent than production databases given log data often less protected than primary storage.
    • •Model providers may train on API requests unless opted out, potentially exposing proprietary information. Enterprise security requires verifying provider data policies, opting out of training data usage, and using dedicated instances where available. For highly sensitive applications, self-hosted models eliminate external data exposure risk entirely. The choice between cloud API and self-hosted depends on data sensitivity versus operational cost, because cloud providers offer convenience but data may be used for model improvement unless contractually prohibited, and even with opt-out, metadata about queries (timing, patterns, volume) reveals business intelligence that competitors could exploit if leaked from provider telemetry.
    • •Output leakage through verbose error messages can reveal system internals or training data. Error responses must be generic ("Unable to process request") with detailed errors logged internally only. Security testing should verify that prompting errors, parsing failures, or unexpected inputs produce safe responses without stack traces, connection strings, or internal reference information. Attackers use error messages to probe system architecture, so production hardening requires removing all debugging information from external responses, with errors categorized as user error (safe to return) or system error (internal only), ensuring attackers cannot distinguish between missing permissions and configuration errors to infer system state.

      Prompt Injection Defense

      Preventing instruction override attacks

      • •Input sanitization removes or escapes characters that could alter instruction interpretation. While LLMs are less vulnerable than SQL injection, attackers can use delimiter injection or instruction override attempts to bypass system prompts. Security review requires testing with common attack patterns: ignoring previous instructions, role-playing as different persona, or extracting system prompt content. Defenses include input validation (rejecting suspicious patterns), instruction delimiter escaping, and post-generation verification checking whether response follows intended instruction, because prompt injection remains active research area without perfect defense, requiring defense-in-depth where multiple layers compensate for any single layer's inevitable vulnerabilities.
      • •System prompt isolation separates immutable instructions from user input. Architecture should clearly distinguish system prompt (developer-controlled, user cannot modify) from user message (free text). Security review verifies that system prompt cannot be overridden by user input, using role-based prompting where model trained to follow assistant role instructions regardless of user attempts to override. Critical safety instructions should be reinforced in multiple ways: system prompt, examples in few-shot demonstrating desired behavior, and post-processing validation, because attackers may find single defense weaknesses, making layered approach more robust where any individual layer failure still caught by others.
      • •Output filtering removes harmful content before returning to users. Even with safe prompt, model may produce inappropriate responses when jailbroken. Security controls include blocklists for known harmful patterns, LLM-based safety classifier, and human review escalation for uncertain cases. Filtering must balance safety against false positives, where over-filtering rejects legitimate responses and under-filtering allows harmful content. Security review requires testing filter effectiveness on adversarial inputs, measuring both detection rate (finding attacks) and false positive rate (rejecting safe queries), because unusable over-filtered system creates workarounds (users rephrase queries to bypass filters) that may inadvertently bypass safety controls designed for specific attack patterns.

        PII Protection

        Preventing personal information exposure

        • •PII detection and redaction before LLM processing prevents model from accessing sensitive information. Enterprise systems should identify and redact PII patterns (SSN, email, phone, address) from inputs, with optional handling for legitimate PII processing (masking, pseudonymization, or explicit consent). Security review requires testing redaction coverage for all relevant PII types, including variations and encoding (base64, URL encoding) that bypass simple pattern matching. Redaction should occur before any LLM processing, including logging and metrics, because PII in prompts persists in logs even if response not containing PII, creating data breach risk from log storage with weaker controls than primary systems.
        • •Data minimization principle applies to LLM inputs: include only necessary context, not entire documents when small excerpts suffice. RAG systems should retrieve and include minimal information needed to answer query, reducing PII exposure surface. Security review requires examining retrieval strategies for over-retrieval where unnecessary documents containing PII included in context. Techniques like retrieving only relevant sections rather than full documents, and filtering retrieved content for PII before inclusion, reduce risk because unnecessary PII in context increases exposure surface without improving answer quality, creating additional compliance burden for data storage and processing that could be avoided through more precise retrieval.

          Compliance Requirements

          Meeting regulatory standards

          • •Data residency for cloud LLM APIs must meet regulatory requirements for data location. Enterprises in regulated industries (finance, healthcare, government) may require data processing within specific jurisdictions. Security review requires verifying provider data center locations, contractual guarantees for data residency, and audit rights. Violating data residency can result in regulatory fines and loss of licenses, making location of embedding generation, vector storage, and LLM inference all subject to compliance review because each component processes potentially sensitive data where cross-border transfer may violate local data protection laws even if data never stored, only processed during request.
