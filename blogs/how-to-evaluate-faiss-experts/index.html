Index Selection Knowledge

Choosing right index for use case

  • •Flat indexes (IndexFlatIP, IndexFlatL2) provide exact search but O(N) scan time, unsuitable beyond 1M vectors. Experts should explain when flat index acceptable (small scale, high recall requirement, baseline for comparison) and when approximate indexes needed. The decision criteria include vector count, dimension, recall requirements, and latency budget, because different scale regimes require fundamentally different index types. Candidates who cannot articulate trade-offs between Flat, IVF, HNSW, and PQ indexes lack practical experience, because index selection determines system's recall-latency Pareto frontier where wrong choice leaves performance unattainable regardless of tuning, making index type primary architectural decision with long-term consequences for system capability and operational cost.
  • •IVF indexes partition vectors into cells, searching only nearest cells during query. Experts should discuss nprobe parameter (number of cells to search) as primary recall-latency control, and how to select number of cells (nlist) based on vector count for optimal performance. Understanding that nlist should scale with sqrt(N) for balanced trade-off demonstrates theoretical knowledge applied to practical tuning. Candidates who cannot explain cell size impact on recall or how to choose nlist for billion-scale indexes may lack depth, because optimal IVF configuration requires understanding relationship between cluster size, query probe count, and distance computation cost, where poor nlist selection either wastes compute (too many cells) or degrades recall (cells too large, probing insufficient neighbors).
  • •HNSW graph indexes provide state-of-the-art recall-speed trade-off but memory-intensive. Experts should discuss graph construction parameters M (connections per node) and efConstruction (dynamic candidate list size) and their impact on build time, memory, and query performance. Understanding that larger M improves recall but increases memory O(N * M) and build time demonstrates practical knowledge. Candidates who cannot explain parameter tuning for billion-scale HNSW or its memory limitations may not have deployed at scale, because HNSW's memory consumption becomes prohibitive at high dimensions without careful M selection and quantization, where experts know when to use HNSW (moderate scale, high recall) versus IVF (extreme scale, memory-constrained) based on infrastructure limitations.

    Quantization Expertise

    Compression without excessive recall loss

    • •Product quantization compresses vectors by dividing into sub-vectors and encoding each with codebook index. Experts should explain PQ parameters: number of sub-vectors (M) and bits per sub-vector (nbits), and trade-offs where more sub-vectors increases recall but reduces compression. Understanding that M should divide vector dimension evenly and typical values 8-64 demonstrates practical experience. Candidates who cannot discuss PQ impact on distance computation speed (lookup tables precomputed) or memory reduction (original float32 vector 4*D bytes to M*nbits/8 bytes) lack deep understanding, because PQ configuration determines system's cost-performance frontier where optimal parameters vary by vector distribution, requiring empirical evaluation rather than default values.
    • •IVFPQ combines IVF clustering with PQ compression, standard for billion-scale search. Experts should discuss how IVF selects cells then PQ decodes only candidate vectors within probed cells, enabling search on compressed representations without full decompression. Understanding the interaction between nprobe and PQ, where more probes increases recall but also more PQ decoding, demonstrates systems thinking. Candidates who cannot explain how to tune PQ codes for specific recall target or discuss trade-offs between higher nprobe vs better quantization may struggle with production tuning, because IVFPQ optimization requires balancing cluster search cost (nprobe) against per-vector decoding cost (PQ parameters) to minimize total latency at target recall, requiring understanding of where bottleneck lies for specific hardware and scale.

      GPU Optimization Skills

      Leveraging parallel hardware for speed

      • •FAISS GPU implementation achieves 5-10x speedup over CPU for certain operations but requires careful memory management. Experts should discuss GPU memory limits (typically 16-80GB) limiting index size, and techniques like streaming or hybrid CPU-GPU indexes for larger collections. Understanding that GPU excels at batch distance computations but has overhead per kernel launch demonstrates practical experience. Candidates who cannot explain when GPU beneficial (large batches, high throughput) versus CPU (low latency, small batches) may over-recommend expensive GPU solutions, because GPU adds significant complexity and cost, appropriate only for workloads where batch size exceeds GPU launch overhead and latency requirements tolerate PCIe transfer times, making many real-time applications better served by CPU despite slower per-vector throughput due to lower per-query latency.

        Performance Tuning

        Optimizing for production workloads

        • •Multi-threading configuration significantly impacts FAISS performance on CPUs. Experts should discuss OpenMP thread settings, NUMA awareness, and batch query processing for throughput optimization. Understanding how FAISS parallelizes distance computation (over vectors) versus index traversal (graph serial) demonstrates systems knowledge. Candidates who cannot explain when to use batch processing (high throughput, offline) versus single-query (interactive, low latency) may not optimize for production query patterns, because FAISS default configurations optimized for throughput at cost of latency, requiring reconfiguration for real-time applications where single-query latency more important than batch throughput.
        • •Memory mapping enables larger-than-RAM indexes by using disk storage with OS page caching. Experts should discuss FAISS's OnDiskInvertedLists for IVF indexes, performance implications (random I/O for index traversal), and when acceptable (read-heavy, moderate latency tolerance). Understanding trade-offs between memory-mapped (cheaper, slower) and in-memory (faster, expensive) indexes demonstrates production experience with cost constraints. Candidates who cannot discuss memory mapping limitations for HNSW (poor locality, random access patterns) or recommend unrealistic in-memory for billion-scale indexes lack practical scale experience, because at extreme scale, memory-mapped indexes become necessary despite latency cost, requiring expert tuning of OS page cache and access patterns to achieve acceptable performance.

          Production Readiness

          Beyond toy examples to deployed systems

          • •Index serialization and versioning for continuous deployment matters for production systems. Experts should discuss FAISS index serialization formats, handling index updates without downtime, and blue-green deployment strategies for new indexes. Understanding limitations like inability to modify IVF clusters after creation without full rebuild demonstrates practical operational experience. Candidates who cannot explain index update strategies (rebuild periodically, incremental IVF with pre-computed clusters) may not have managed evolving collections, because real systems require index updates as documents change, and naive approach of full rebuild for each update becomes impossible at scale, requiring sophisticated strategies like maintaining multiple indexes or using hybrid architectures that combine real-time search with periodic full rebuilds.
          • •Monitoring and profiling FAISS performance in production requires understanding internal metrics. Experts should discuss measuring effective recall, latency percentiles, and throughput under load, with tools for profiling distance computation bottlenecks. Candidates who cannot explain how to detect index degradation from data distribution shift or query pattern changes lack production monitoring experience, because static performance benchmarks often degrade as production data evolves, requiring ongoing monitoring and recalibration where recall drop detected through systematic evaluation rather than user complaints, enabling proactive index retraining or parameter adjustment before quality falls below acceptable threshold.
